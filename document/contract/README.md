# 계약서 특약 구역 추출

계약서(PDF 또는 사진)를 읽어 특약사항 칸을 찾고, 양식에 인쇄된 기본특약(①-⑥)과 당사자가 직접 쓴 특약(※ 기타 아래)을 나눠서 넘깁니다. 개인정보(주민번호·전화·계좌·전자우편·당사자 이름)는 가린 뒤 넘깁니다. 특약 해석(불리한 특약, 필수 특약 누락 판단)은 하지 않습니다. 그 일은 AI 모듈이 이 결과를 받아서 합니다. LLM 호출은 없습니다.

결과는 [분석 결과 형식](../../docs/analysis-result.md)의 `special_terms` 조각이고, [위험 등급 모듈](../risk/README.md)의 `build_analysis_result(special_terms=...)`에 그대로 넘깁니다.

## 설치와 실행

```bash
pip install -r document/contract/requirements.txt
python -m unittest discover -s document/contract/tests -v   # 저장소 루트에서
```

- 글자 층이 있는 PDF는 `pdfplumber`로 바로 읽고, 사진과 스캔 PDF는 OCR합니다.
- OCR 엔진은 RapidOCR(PaddleOCR 한국어 PP-OCRv5 모델을 onnxruntime으로 실행)입니다. PaddlePaddle은 Python 3.14 Windows 설치 파일이 없어서 같은 모델을 onnx로 돌리는 쪽을 골랐습니다. 처음 실행할 때 모델(약 20MB)을 내려받습니다.
- 다른 엔진을 쓰려면 `analyze_contract(..., engine=함수)`로 넘깁니다. 함수는 그림(PIL.Image)을 받아 `[(글자, 네 꼭짓점 좌표, 점수), ...]`를 돌려주면 됩니다.
- 샘플 비교 테스트는 `CONTRACT_SAMPLES_DIR` 환경변수에 샘플 폴더를 주면 돕니다. 샘플은 저장소에 넣지 않습니다.

## 사용법

```python
from document.contract import analyze_contract
from document.risk import build_analysis_result

terms = analyze_contract("계약서.pdf")                       # 경로, bytes, 파일 객체
terms = analyze_contract(["1쪽.jpg", "2쪽.jpg"])              # 사진 여러 장은 쪽 순서대로
result = build_analysis_result(..., special_terms=terms)
```

`analyze_contract`는 예외를 내지 않습니다. 실패하면 `extraction_status: "failed"`, `reason_code: "PARSE_FAILED"`이고 AI 모듈은 특약 누락을 판단 보류로 처리합니다.

| 상황 | reason 예 |
| --- | --- |
| PDF·사진이 아니거나 손상 | "지원하지 않는 파일 형식입니다", "PDF를 열 수 없습니다" |
| OCR 엔진이 설치되지 않음 | "사진을 읽을 OCR 엔진이 없습니다" |
| 글자를 하나도 못 읽음 | "밝은 곳에서 문서 전체가 나오게 다시 찍어 주세요" |
| 특약사항 칸이 없음 | "특약사항이 있는 쪽을 포함해 올려 주세요" |

## 결과

| 키 | 내용 |
| --- | --- |
| `extraction_status` | `ok` / `failed` |
| `section_text` | 가린 특약 구역 전체. 기본특약 한 항목당 한 줄, `※ 기타`, 직접 쓴 특약 한 항목당 한 줄 |
| `page`, `pages` | 특약 칸이 있는 첫 쪽, 걸친 쪽 전부 |
| `form` | `standard_2023`(기본특약 핵심 문구 3개 이상 확인) / `unknown` |
| `base_terms[]` | 기본특약. `no`(1-6), `text`, `note`(④ 아래 ※ 안내처럼 따로 줄에 있는 안내), `choice`, `choice_status` |
| `section_status` | 구역별 상태 `{"base_terms": ..., "custom_terms": ...}`. `read`(읽음) / `empty`(비어 있음) / `failed`(추출 실패). 아래 표 |
| `custom_marker_found` | `※ 기타` 표시를 찾았는지 |
| `custom_terms[]` | 직접 쓴 특약. `no`, `text`. 번호(1. 2. …)로 나누고, 번호가 없으면 문장 끝(…다.)에서 나눔 |
| `custom_terms_text` | 직접 쓴 특약만 이은 텍스트. 없으면 `null` |
| `masked`, `masking.counts` | 마스킹 처리를 했는지, 종류별로 가린 개수 |
| `external_send_allowed`, `masking.residual_risks` | 외부 LLM에 보내도 되는지, 마스킹 뒤에도 남은 위험(`ADDRESS`, `POSSIBLE_NAME`). 아래 "외부 전송" 참고 |
| `source` | `text_layer` / `ocr` / `mixed` |
| `ocr_score` | 특약 칸 OCR 신뢰도 평균(0-1). 글자 층 PDF면 `null` |
| `warnings[]` | 아래 표 |

### 기본특약과 직접 쓴 특약 나누기

- 칸 시작은 `[특약사항]` 같은 짧은 머리말 줄, 끝은 서명란 문구("본 계약을 증명하기 위하여", "서명 또는 날인")입니다. 쪽 번호(`- 2 / 4 -`)는 뺍니다.
- `※ 기타` 위는 기본특약, 아래는 직접 쓴 특약입니다. OCR이 `※기타 1.임차인은…`처럼 한 줄로 붙여도 나눕니다.
- 기본특약 번호는 ①-⑥ 글자로 찾고, 번호를 못 읽으면 핵심 문구(예: "상세주소부여")로 찾습니다.
- 표준계약서가 아닌 계약서(①-⑥도 ※ 기타도 없음)는 특약 칸 전체를 직접 쓴 특약으로 봅니다.
- `※ 기타` 아래 양식 안내·예시 문구("약정할 사항이 있으면 기재", "[대항력과 우선변제권 확보 관련 예시] … 특약 가능")는 지웁니다 `[추측]` 양식 판본마다 문구가 다를 수 있어 실제 양식으로 확인이 필요합니다.

### 구역별 상태 (팀 합의 2026-11-27)

OCR 실패가 "특약 없음"으로 보이지 않도록 직접 쓴 특약은 확실할 때만 `empty`로 둡니다.

| 구역 | read | empty | failed |
| --- | --- | --- | --- |
| `base_terms` | 기본특약을 찾음 | 기본특약 구역이 없음(표준계약서가 아님) | 표준계약서인데 ①-⑥ 중 일부를 못 찾음, 또는 추출 실패 |
| `custom_terms` | 직접 쓴 특약을 찾음 | `※ 기타`를 찾았고 아래가 비어 있음 (OCR 신뢰도 정상, 칸 끝도 찾음) | `※ 기타`를 못 찾음, OCR 신뢰도 낮음, 칸 끝을 못 찾음, 또는 추출 실패 |

`custom_terms`가 `failed`이면 위험 등급 모듈이 전체 요약에 "특약 확인 필요"(`SPECIAL_TERMS_CHECK_NEEDED`)를 넣습니다.

### 체크박스 (④ 분쟁조정, ⑤ 재건축 계획, ⑥ 상세주소 동의)

| choice_status | 뜻 |
| --- | --- |
| `selected` | ■ 등 채운 표시 뒤의 선택지를 `choice`에 넣음 |
| `none_selected` | 모든 선택지가 □ (아무것도 안 고름) |
| `unreadable` | 표시를 못 읽음. 사진 OCR은 ■□를 거의 읽지 못해서 대부분 이 값입니다. `choice`를 추측하지 않습니다 |

### warnings

| 코드 | 뜻 |
| --- | --- |
| `CUSTOM_MARKER_NOT_FOUND` | `※ 기타`를 못 찾음. 직접 쓴 특약이 기본특약 마지막 항목에 붙었을 수 있음 |
| `BASE_TERMS_INCOMPLETE` | 표준계약서인데 기본특약 ①-⑥ 중 일부를 못 찾음 |
| `NO_CUSTOM_TERMS` | 직접 쓴 특약이 없음 (정말 없는 경우와 못 읽은 경우 둘 다) |
| `LOW_OCR_CONFIDENCE` | 특약 칸 OCR 신뢰도 평균이 0.80 미만 |
| `END_MARKER_NOT_FOUND` | 서명란을 못 찾아 문서 끝까지 특약 칸으로 봄 |

## 개인정보 마스킹

| 대상 | 바꾼 모양 |
| --- | --- |
| 주민등록번호·외국인등록번호 | `******-*******` |
| 전화번호 (휴대폰, 지역번호, 하이픈 없는 휴대폰) | `***-****-****` |
| 계좌번호처럼 보이는 숫자 (하이픈으로 나뉜 숫자 10자리 이상, 날짜 제외) | `[계좌번호]` |
| 전자우편 | `[전자우편]` |
| 당사자란 성명·대표 칸에서 읽은 이름 | `***` |

- 금액, 날짜, 조항 번호는 그대로 둡니다.
- 당사자란에 없는 이름(특약에만 나오는 사람)은 가리지 못합니다.
- 주소는 가리지 않습니다(특약의 주소는 대부분 임차 주택 주소). 팀 합의가 필요합니다.

### 외부 전송 (`external_send_allowed`)

`masked: true`는 마스킹 처리를 했다는 표시일 뿐, 개인정보가 남지 않았다는 보장이 아닙니다. 그래서 외부 LLM 전송 여부를 따로 둡니다. AI 모듈은 `external_send_allowed`가 `true`일 때만 특약 텍스트를 외부로 보냅니다.

| 남은 위험 | 잡는 모양 |
| --- | --- |
| `ADDRESS` | 도로명주소(`동일로 1414`), 동·호수(`101동 707호`), 지번(`상계동 123-4번지`), 시·도+시·군·구(`서울특별시 노원구`) |
| `POSSIBLE_NAME` | 역할 뒤에 띄어 쓴 2-4글자 + 조사 (`임차인 홍길동은`). 당사자란에 없어서 못 가린 이름 |

- 하나라도 남으면 `external_send_allowed: false`입니다. 잘못 잡아도 전송만 막히고 결과는 그대로라 보수적으로 잡습니다.
- 마스킹을 끄면(`mask=False`) 항상 `false`입니다.
- OCR이 띄어쓰기 없이 읽은 이름(`임차인홍길동은`)은 잡지 못합니다 [한계].

## 샘플 확인 (2026-11-27)

가짜 계약서 샘플(2023.10 표준계약서 양식, 저장소 밖 보관)로 확인했습니다.

| 입력 | 기본특약 | 직접 쓴 특약 | 글자 일치(공백 무시) | 체크박스 |
| --- | --- | --- | --- | --- |
| 글자 층 PDF (4쪽) | 6/6 | 5/5 | 100% | ④ 동의, ⑤ 없음, ⑥ 선택 안 함 모두 맞음 |
| 휴대폰 사진 2장 (약 2.5도 기울어짐) | 6/6 | 5/5 | 96-100% | 모두 `unreadable` |

사진에서 처음에는 줄이 여럿 빠졌는데, 두 가지를 바꿔서 해결했습니다.

- RapidOCR 기본 글자 방향 분류기를 껐습니다. 기울어진 줄을 거꾸로 판단해 "을", "o" 같은 조각만 나왔습니다.
- 검출 크기 제한을 736에서 2000으로 올리고, 글자 상자 기울기를 재서 0.5도 넘게 기울면 반듯하게 돌린 뒤 다시 읽습니다.

## 아직 안 한 것

- 사진 체크박스(■□) 판정. 칸 그림의 어두운 정도로 판정하는 방법을 생각하고 있지만 아직 만들지 않았습니다.
- 손글씨 특약. 샘플은 인쇄 글자뿐이라 손글씨 인식률은 확인하지 않았습니다.
- 계약서 본문 항목(임대인 이름·보증금·주소) 추출. `OWNER_MISMATCH`, `STANDARD_CONTRACT_NOT_USED` 신호에 필요합니다.
- `.docx`·`.hwp` 계약서. 지금은 PDF와 사진만 받습니다.
